# Recipe Recommender RAG

A production-grade Retrieval-Augmented Generation system that answers natural-language recipe queries against a corpus of 1,000+ recipe documents.

**Example queries:**
- *"What can I make with leftover chicken and lemon?"*
- *"Give me a low-carb dessert under 30 minutes."*
- *"Vegan soup for cold weather"*

---

## How It Works

```
User Query
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  RETRIEVAL  (src/retriever.py)                      │
│                                                     │
│  1. Embed query  →  384-dim vector                  │
│     (all-MiniLM-L6-v2, same model as ingestion)    │
│                                                     │
│  2. Dietary keyword detection  (src/filters.py)     │
│     vegan / keto / gluten-free / low-carb / …      │
│          │                                          │
│    ┌─────┴──────┐                                   │
│    │ tags found │  pre-filter chunk_store by tags   │
│    │            │  → brute-force IndexFlatL2        │
│    │  no tags   │  → IVFFlat nprobe search          │
│    └─────┬──────┘                                   │
│          │                                          │
│  3. Return top-K chunks + L2 score + latency_ms     │
└─────────────────────────────────────────────────────┘
    │
    ▼
Streamlit UI  (app/streamlit_app.py)
```

### Ingestion Pipeline (offline, one-time)

```
data/  (.txt / .docx / .pdf)
    │
    ▼  Phase 1 — Discover files
    ▼  Phase 2 — Parse  (TxtParser / DocxParser / PdfParser)
    │           State-machine extracts: Title, Tags, Prep/Cook/Serves,
    │           Ingredients, Method, Chef Tips
    ▼  Phase 3 — Chunk  (one chunk per section, never merged)
    │           chunk_id = "{recipe_id}_{section}"
    │           metadata: tags, prep_time_mins, cook_time_mins, serves
    ▼  Phase 4 — Embed  (all-MiniLM-L6-v2, batch=128, L2-normalised)
    ▼  Phase 5 — Index  (FAISS IVFFlat, nlist=64)
    │
    └─→  index/recipe.index
         index/chunk_store.pkl
         index/embeddings.npy
         index/manifest.json
```

## Usage

### Step 1 — Build the index (one-time)

```bash
python scripts/build_index.py
```

Optional flags:
```
--data-dir  PATH   Recipe corpus directory (default: data)
--nlist     INT    IVFFlat cluster count (default: 64; use 256 at 50K chunks)
```

Expected output for the included corpus (1,053 files → 3,159 chunks):
```
[1/5] Found 1053 recipe files
[2/5] Parsed 1053 recipes (0 errors)
[3/5] 3159 chunks  (ingredients=1053, method=1053, tips=1053)
[4/5] Embedding 3159 chunks …
[5/5] Building IVFFlat index (nlist=64) …
✓ Done. Index saved to index/
```

### Step 2 — Launch the app

```bash
streamlit run app/streamlit_app.py
```

The app opens at `http://localhost:8501`. Features:

| Sidebar control | Description |
|-----------------|-------------|
| Top-K | Number of results (1–20, default 5) |
| nprobe | Clusters to search (1–64, default 10) |
| Dietary pre-filter | Toggle automatic tag filtering from query |
| Section filter | Show only ingredients / method / tips chunks |
| Compare mode | Side-by-side filtered vs unfiltered when dietary tags detected |

### Using the retrieval API directly

```python
from src.retriever import retrieve_recipes

results, latency_ms = retrieve_recipes(
    query="low-carb chicken soup",
    top_k=5,
    nprobe=10,
    use_filter=True,   # auto-detects "low-carb" → filters by tag before search
)

for r in results:
    print(r["title"], r["section"], r["score"])
```

## nprobe Tuning

```bash
python scripts/evaluate_nprobe.py
```

Benchmarks nprobe ∈ {1, 5, 10, 50} on 3 spec queries, measuring Recall@5 vs exhaustive search and latency averaged over 5 runs.

Results with the included corpus (nlist=64, ~3K chunks):

| nprobe | Recall@5 | Coverage |
|--------|----------|----------|
| 1 | ~60% | 1.6% |
| 5 | ~100% | 7.8% |
| 10 | 100% | 15.6% |
| 50 | 100% | 78.1% |

**Production default:** `nprobe=10` — full recall at 15.6% index coverage.

## Key Design Decisions

**Section-level chunking** — one chunk per recipe section (ingredients / method / tips), never merged. This ensures each embedding carries enough signal for ingredient-based and dietary-filter queries without dilution from unrelated sections.

**Same embedding model at ingestion and query time** — `all-MiniLM-L6-v2` (384-dim, L2-normalised). A guard prevents a hash-based dev shortcut from reaching production: the `RECIPE_EMBEDDER_MODEL` env var is cross-checked at startup, and the `index/manifest.json` records the model name and is validated at load time.

**Pre-filter path** — when dietary keywords are detected in the query, the chunk store is filtered by tags first, then an in-memory `IndexFlatL2` searches only the matching subset. This avoids returning irrelevant results when the user explicitly requests dietary restrictions.

**IVFFlat → HNSW migration path** — `nlist=64` for ~3K chunks. Rebuild with `nlist=256` at 50K chunks; migrate to HNSW at 500K.

## Scaling Guide

| Corpus size | nlist | nprobe | Index type |
|-------------|-------|--------|------------|
| < 10K chunks | 64 | 10 | IVFFlat |
| 10K–100K chunks | 256 | 32 | IVFFlat |
| 100K–500K chunks | 1024 | 64 | IVFFlat |
| 500K+ chunks | — | — | HNSW |

Rebuild the index after any corpus change: `python scripts/build_index.py`.
